# Experimental local browser receiver bridge

`experimental-browser-receiver` adds a **default-off library interface** connecting an authenticated transport adapter to the real local browser request store. It has no CLI activation, network listener/poller, production transport verifier, device enrollment, browser control endpoint or provider integration. Compiling the feature does not grant remote authority. No existing Cloud login/sync session automatically becomes a browser execution grant.

The trusted embedding application selects an existing credential explicitly with `prepare`: project, partition, name, exact HTTPS origin, opaque account reference and owner-declared custodian profile label. It also supplies the expected issuer/owner/tenant/client/device identity. The selection resolves and retains the credential ID, a fresh opaque revision, the finite owner-session binding and a vault write generation. It expires within five minutes or at session expiry, whichever comes first. It is not device enrollment, provider authentication, or proof of OS/profile isolation.

`receive` accepts at most 8 KiB through an `AuthenticatedTransport` implementation. That trusted adapter must verify message integrity and derive the principal from actual issuer/client/device authentication and registry policy; merely deserializing a principal or a `verified` flag is not an implementation. **No such production adapter ships in this slice.** The synthetic HMAC adapter exists only in unit-test code. Provider authentication and enrollment policy remain a separate private gateway integration decision; this bridge does not invent them.

The local handle is selected by the embedding process, not by a remote caller choosing arbitrary local state. Every delivery must match its binding and principal. Request origin/account/profile/revision must match the local selection exactly. No password, wisp token, credential name, vault path, arbitrary destination or approval result is accepted through the remote command interface. Acknowledgements and status/cancellation use the same authenticated principal and binding.

Admission atomically writes the browser request, replay journal, audit and queued status event. Identical job redelivery returns the durable state; changing a reused job's binding fields fails. The native host includes the transport identity and owner-declared account/profile in its approval details, and retains Windows Hello/macOS Touch ID verification. Linux still refuses native approval. The existing extension's private document Port, navigation checks and human submission remain unchanged; the profile label is not an attestation that those isolation prerequisites have been met.

At actual release the bridge checks both journal/request links, current local revocation, scope and credential identity, expiry, owner session and the captured write generation. Credential/auth/project/partition writes conservatively invalidate prepared bindings, including unrelated changes and ABA. Reprepare through the trusted owner frontend; do not silently update or broaden a binding. The session file lock and SQLite transaction protect the final checks and release commit. Only the existing native host receives the existing plaintext payload; the receiver API and outbox contain metadata only.

Durable states are `queued`, `release-committed`, `filled`, `denied`, `cancelled`, `expired` and `outcome-unknown`. `release-committed` is recorded atomically before the native response can return. It does not assert browser receipt. Successful completion means fields were filled, never that a form was submitted or an account authenticated. Cancellation before release stops it. After release may have occurred, cancellation/restart becomes `outcome-unknown`; it cannot recall an exposed password or cancel a provider action. A remote revocation not yet delivered locally cannot invalidate a previously admitted lease retroactively. Its maximum offline validity is bounded by the local selection and job expiry.

`outbox` returns at most 64 metadata events for the selected local binding. An authenticated acknowledgement removes only that binding's events through an existing sequence. Retrying event delivery never retries release. Persist a protected local binding ID and use `restore_local_binding` plus `reconcile_after_restart` after process restart: a committed release without a durable fill result becomes unknown. Do not call restart reconciliation during an active fill. A stale session, revoked binding or changed selection cancels pending work. Journal entries are retained to reject replay; this slice caps bindings at 64, jobs at 1,024, pending browser requests at 32 and unacknowledged events at 4,096. There is no automatic pruning that forgets replay protection.

Schema 16 adds the request marker, journal/outbox and write-generation triggers. The guard remains in default builds, which refuse receiver-marked releases. Prior schema-15 clients reject this newer schema rather than ignore the guard. Browser requests, receiver selections, replay journal and outbox are not included in portable exports or full encrypted backups; a restored vault does not restore execution authority. This is not protection against an owner deliberately editing the database/schema or rolling back the entire vault.

Tests run the actual Rust vault, journal, browser release and completion functions in isolated child processes with disposable accounts. They cover authenticated-message rejection, exact selection, duplicate/replayed jobs, concurrent delivery/release, scope/identity changes, ABA, cancellation/revocation, session lock, expiry, atomic rollback and restart after release. A test-only native approval outcome exercises the production release function; it does not prove physical user presence. Canary checks inspect output, audit and outbox. Full native presence, installed extension/custodian isolation and live provider acceptance remain unperformed.

For an eventual usable Cloud-connected flow, complete the private authenticated gateway/device transport, supported custodian setup, native-host/extension installation and narrowly scoped result observer. Obtain concrete owner authority before enrollment/session custody or deployment. An authenticated account/dashboard verdict needs a separately reviewed bounded observer after human submission, not a generic DOM, cookie, browser or secret getter.
