# Cross-node credential operations — contract draft

Status: **RUG-446 review draft, not an implemented or approved interface.** This defines the proposed boundary for [RUG-445](https://linear.app/rankupgames/issue/RUG-445/track-scoped-cross-node-credential-operations). [RUG-447](https://linear.app/rankupgames/issue/RUG-447/enforce-named-ssh-and-sudo-credential-operations) and [RUG-448](https://linear.app/rankupgames/issue/RUG-448/provision-and-revoke-environment-scoped-runtime-credentials) depend on user approval of this contract before either runtime child proceeds. No DEV-1/DEV-2 host, account, Kubernetes context, or credential is a product default. This repository contains no DEV-1/DEV-2 operator configuration or evidence that its local `exec` path was used successfully there. The historical csos workspace/operator reference was unavailable in this workspace; the operator must supply and verify exact references separately.

## Trust boundary and ownership

The vault, unlocked session, policy/configuration, and operation executor stay on a trusted local machine or approved automation runner. A separate owner or delegated administrator controls the private operation catalog and issues bounded authorizations. An agent or workload may request a named operation but cannot author its own target, command, credential, grant, or environment ownership. Only the named restricted host helper may receive the selected host-operation input, which may be a sudo credential for that operation. A runtime receives only its selected application credential. Never transfer the vault database, master password, session/protector, a general host credential to an application or unrelated operation, or an unrestricted `wk_*` token to any target.

The executor must obtain **trusted requester identity** from the authenticated transport/process boundary defined by [RUG-8](https://linear.app/rankupgames/issue/RUG-8/add-trusted-agent-identity-to-policy-evaluation), not from a CLI flag, environment variable, prompt, request label, or SSH username supplied by the requester. Until that provenance exists for an entry point, cross-node requests through it are disabled. Identity must bind to a stable principal and authentication event, and every authorization and execution must re-evaluate it. An owner running `wispkey exec` is a different trust path and does not implicitly become an agent identity. Existing instance authentication is scoped to proxy token substitution, not proof of a cross-node operation principal.

The trusted runner and a privileged destination can read the delivered plaintext. WispKey cannot protect it against compromise of either, against a malicious fixed helper, or after a runtime consumes it. The application environment must never receive a host sudo credential. The feature is local-first: it does not require cloud sync, a second vault, an always-on central broker, or a general remote secret-fetch endpoint.

## Proposed public surfaces and private configuration

These names and schemas are proposals for review, **not current commands**. Preserve the existing `exec`, `run`, `inject`, proxy, and MCP behavior. Introduce a separate `wispkey operation check|authorize|execute|cancel|status` surface for host operations, and `wispkey environment check|deliver|refresh|revoke|status` for runtime delivery. `check` performs secret-free validation; `authorize` is owner-only and creates a one-use grant; `execute` consumes its opaque grant ID through an authenticated requester channel. `cancel` and `status` accept an attempt ID and return metadata only. Environment actions use the same grant machinery, with one grant per delivery/refresh/revoke and idempotency keys for provider writes. Neither surface accepts a free-form command, target URL, namespace, credential value, or secret-bearing argument at execution time. Do not add an MCP plaintext retrieval or arbitrary remote execution tool. JSON and text outputs use the same status allowlist.

Owner-controlled configuration is a versioned, private file (proposed `~/.wispkey/operations.toml`), loaded with owner-only permission checks and strict unknown-field rejection. Each catalog entry has a unique operation ID and kind; immutable project plus credential **ID** resolved during owner review (a name may appear for human selection, but later renames or same-named cross-project records cannot retarget it); trusted requester principal(s); environment owner ID; target ID; delivery channel; maximum grant TTL and runtime; concurrency cap; and an exact command/helper or provider action. Empty, malformed, absent, revoked, archived, or out-of-project references deny before any process or provider call. The catalog is policy input, not a source of plaintext. Changes to target identity, operation semantics, credential ID, or ownership invalidate outstanding grants.

Illustrative schema only; every value is synthetic, and a real catalog must use verified immutable IDs and a real pinned host key:

```toml
version = 1

[[operation]]
id = "example-maintenance"
kind = "ssh-helper"
project_id = "project-example-id"
credential_id = "credential-example-id"
requester_principal = "runner-example-id"
environment_id = "environment-example-id"
target_id = "host-example-id"
account = "restricted-example"
host_key_sha256 = "SHA256:placeholder-never-trust"
helper_id = "maintenance-helper-v1"
delivery = "stdin"
max_grant_seconds = 300
max_runtime_seconds = 60
max_concurrency = 1

[[operation]]
id = "example-runtime-delivery"
kind = "kubernetes-secret"
project_id = "project-example-id"
credential_id = "app-credential-example-id"
requester_principal = "deployment-runner-example-id"
environment_id = "environment-example-id"
target_id = "cluster-example-id"
namespace_uid = "namespace-example-uid"
secret_name = "app-secret-example"

max_grant_seconds = 300
max_runtime_seconds = 60
max_concurrency = 1
```

The recommended initial targets are one restricted SSH helper and one named Kubernetes Secret from an operator-supplied K3s context, after verification of the live destination and consumer. Docker and private-file adapters remain contract shapes, not first-slice commitments. Implementation should use typed provider-specific target blocks; this illustration lists binding fields without freezing parser syntax.

Host targets additionally record a fixed network destination, account, pinned SSH host public-key fingerprint and dedicated known-hosts entry, and a fixed remote helper/protocol version. Environment targets record provider type, authenticated cluster/engine endpoint identity, context/namespace or Docker target, environment/owner ID, destination object identity, consumer contract, and storage/permission requirements. DEV-1/DEV-2 are merely possible values in private operator configuration. A provider adapter must verify those fields from the live authenticated destination, including namespace or destination UID where available, before delivery; context labels or aliases alone are insufficient.

The owner can approve only one catalog entry and one exact requester/target/environment tuple at a time. Distinguish the stable catalog **operation ID**, one-use **grant ID**, and per-execution **attempt ID**. A grant records its ID, catalog revision, credential ID/revision, requester principal, target identity, environment, issued/expiry time, one permitted use, and state. It contains no secret and is stored on the runner. The requester gets only its opaque ID. Default maximum grant lifetime is 300 seconds and default total execution time is 60 seconds; the catalog may lower either, never make either unbounded, and must define a finite connection deadline within the execution limit. A grant cannot outlive the owner's configured maximum or the authenticated session/authorization lifetime. Expired, canceled, reserved, consumed, changed, or wrong-principal grants deny. Authorization is not inferred from possession of a grant ID alone. No waiting queue may start an attempt after expiry.

## Host operation execution (RUG-447)

Resolve and authorize everything **before decrypting**. Compare the authenticated requester to the grant and catalog, verify the credential ID/revision and environment, reserve the grant atomically with a durable `started` audit row, then connect only to the fixed target. Reservation and required audit writes must succeed before plaintext release; their failure denies execution. SSH must authenticate the exact pinned host key for the target ID, even if DNS, a hostname alias, user SSH config, or a jump configuration changes. Use an isolated known-hosts file and explicit noninteractive, strict host-key options; disable opportunistic new-key acceptance, forwarding, user config overrides, multiplexed sessions, and unexpected proxy/jump routes. Verify the fixed remote account. Account for OpenSSH [host-key alias and configuration precedence](https://man.openbsd.org/cgi-bin/man.cgi/OpenBSD-current/man5/ssh_config.5), and prove the effective options in tests. Host-key rotation requires an owner-reviewed catalog change and fresh grants. A server presenting another host key, including one reached through an alias, receives no secret.

The remote invocation is a fixed, versioned helper or restricted account/forced command, with separately encoded non-secret parameters, never a requester-composed shell string. A sudo operation may use a narrow target-side helper with an exact sudoers rule. The selected secret reaches only the designated child input: a private pipe/stdin protocol or a private short-lived file when the consumer requires one. No secret in argv, shell history, parent environment, SSH command text, terminal echo, tracing, logs, metrics, errors, or returned status. A generic `ssh ... "sudo ..."` shell fragment is not an approved operation. The helper must reject unknown commands, account changes, extra parameters, and unexpected protocol versions. Do not send a sudo password to an application pod.

Execution has a bounded connection deadline and total runtime. Cancellation or timeout closes the input channel, terminates the local SSH child/process group, attempts target-side cancellation by attempt ID, and persists `canceled`, `timed_out`, or `outcome_unknown` according to observed evidence. The target must make a repeated attempt ID idempotent or explicitly report `outcome_unknown`; a lost acknowledgement never triggers automatic second secret delivery. An atomic grant reservation prevents concurrent consumers and replay. A crash or timeout never returns a reserved grant to reusable state. Per-operation and per-target concurrency caps fail closed, with no queuing beyond grant expiry. Failure to persist terminal state returns a safe `outcome_unknown` response and requires owner reconciliation; it must not auto-retry. Revocation prevents new starts; it cannot claw back plaintext already consumed or guarantee termination of a privileged remote command if the target is unreachable. Report that limit explicitly.

## Runtime credential delivery (RUG-448)

Host authority and application runtime authority use separate catalog entries and separate credentials. An environment grant binds a trusted deployment principal, exact provider endpoint identity, environment owner, target cluster/context/namespace (or Docker engine and allocation), destination object, and credential ID. It cannot read or write another environment's Secret, file, volume, database, bucket, or identity realm. Use a least-privilege provider identity restricted to that destination. The initial Kubernetes adapter may update only an operator-precreated exact Secret bound by cluster endpoint/CA identity, namespace UID, Secret name and UID, and independently verified owner configuration; namespace or object labels alone are not ownership proof. Its service account should have `get`/`update` for that named object only, with no namespace-wide create/list permission. A named kubeconfig context is only a selector. Docker delivery similarly verifies the engine endpoint and destination allocation. A private-file adapter must create atomically under a verified owner-controlled directory with owner-only permissions and a bounded lifetime. Kubernetes Secret base64 is transport encoding, not encryption: the generic Secret API cannot attest the cluster's [at-rest encryption configuration](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/). Require independent, owner-controlled, short-lived posture evidence bound to the approved endpoint/CA, cluster identity, and encryption config revision. If the evidence is missing, stale, or mismatched, disable the adapter; do not trust an annotation or flag as proof. [Secret consumer behavior](https://kubernetes.io/docs/concepts/configuration/secret/) affects refresh: mounted volumes update eventually, `subPath` mounts do not receive automated updates, and environment variables require process restart. A provider that cannot verify these properties is unavailable for delivery. This contract requires no live control-plane read or cluster change now.

Delivery is idempotent by `(environment, destination, credential revision, idempotency key)` and reports whether the target committed that exact revision. Before any provider release, the one-use grant reservation and required `started` audit row must commit durably; a write failure denies delivery. Refresh revalidates identity, ownership, authorization, target, and TTL before each write. Authorization expiry stops further delivery/refresh; it does **not** delete a database, bucket, realm, volume, or other retained application data. Rotation uses a new credential revision, delivers it, waits for provider acknowledgement and consumer reload/health evidence, then retires the old credential at its actual issuer. If the issuer cannot revoke it, report `revocation_unverified` and keep the operation open. Removing a Secret or file does not revoke copied credentials, already-running process environments, cached connections, or upstream tokens. Revocation must stop future access by withdrawing provider permissions or replacing/invalidating the credential at the issuer, verify rejected use with a safe synthetic probe where possible, and record any consumer that needs restart. The actual consumer reload and issuer revocation interfaces remain to be specified by the destination owner; approving this contract does not establish or implement those interfaces. On unreachable targets, preserve the last confirmed state and report `outcome_unknown`; do not claim successful rollback or delete retained data. Terminal persistence failure also returns `outcome_unknown` without reusing the reserved grant.

## Output and audit

Do not inherit child stdout/stderr into an agent-visible terminal. Keep them in bounded private memory only long enough to validate a dedicated versioned helper response, then discard raw bytes; never persist or return either stream. The structured response may contain only the expected attempt ID, fixed outcome enum, and bounded non-secret counters. Unknown or mismatched IDs, fields, enums, malformed/oversized output, or tracing produce a safe failure code. Tests deliberately make children emit synthetic canaries through stdout, stderr, exceptions, and partial/streamed chunks, and assert none reaches returned or persisted output; runtime safety cannot rely on recognizing a known canary or redacting arbitrary child text. [RUG-432](https://linear.app/rankupgames/issue/RUG-432/security-investigate-credential-exposure-in-agent-tool-output-and-add) owns pre-persistence tool/output redaction across the agent bridge; this operation path must suppress raw output even before that broader fix lands. Do not use the paused affected credential or raw incident history for testing. Redaction is defense in depth, not a license to return arbitrary child output.

The cross-node audit schema has exactly six allowlisted fields: `timestamp`, authenticated `requester` (or `identity_missing` on denial), stable catalog `operation`, canonical `target`, `environment`, and fixed-enum `result`. Results include `authorized`, `denied_identity`, `started`, `succeeded`, `failed_child`, `timed_out`, `canceled`, `outcome_unknown`, and `revocation_unverified`. It must not contain command text, arbitrary reason strings, full paths, aliases, credential values, tokens, child output, or provider response bodies. Emit a durable row for authorization, denial, start, completion, timeout, cancel, and revocation outcome; if a required pre-release row cannot be persisted, deny before delivery. A terminal write failure leaves a non-reusable grant and safe uncertain status. Existing audit rows are not evidence that agent-visible tool output is safe.

Text/JSON `status` is separately allowlisted to `operation_id`, `grant_id`, `attempt_id`, canonical target/environment IDs, fixed outcome, timestamps, and a validated numeric child exit code when one exists. IDs are generated opaque references, not credential or authorization capabilities by themselves; status still checks the requester/owner. Provider diagnostics are fixed error codes, never raw API strings. An unreachable target or unconfirmed remote result returns `outcome_unknown`, not a guessed exit code. Audit export keeps the six-field audit schema, while status gives the caller enough information to cancel or reconcile one attempt.

## Focused implementation test matrix

Use disposable vaults, fake SSH/sudo executables and provider APIs, two synthetic environments, and synthetic canaries. Tests inspect rendered output and persisted/exported audit with pass/fail checks; they never print the canary.

| Area | Positive evidence | Denials and failure evidence |
| --- | --- | --- |
| Identity/grant | Trusted principal executes its exact one-use grant before expiry; grant reservation and `started` audit commit atomically before release. | Missing/spoofed principal, wrong principal, missing/empty/malformed credential reference, changed credential ID/revision, expired/canceled/replayed grant, concurrent double-use, audit/state write failure, crash after reservation. |
| SSH/host | Fixed helper receives one private input on pinned key/account; safe exit status retained. Use a controlled SSH server fixture for host-key verification in addition to fake process tests. | Wrong key, DNS/alias substitution, changed account, unapproved command/parameter, user SSH config or jump override, auth failure, unapproved sudo escalation. Assert no input was sent before host verification. |
| Runtime/limits | Bounded operation completes; cancel and timeout stop local delivery; concurrency cap holds. | Connection stall, child failure, lost acknowledgement, cancel race, target unreachable, terminal persistence failure; report `outcome_unknown` when remote completion cannot be established, and never reuse a reserved grant. |
| Output/audit | Structured status and allowlisted audit only; no canary in argv, text/JSON, logs, exports, or metrics. | Canary on stdout/stderr, shell tracing, exception, nonzero exit, partial/streamed chunks, malformed/oversized response, escaped/encoded fixture forms; no raw output persists. |
| Environment | Correct deployment principal updates its own precreated named Secret in each of two synthetic targets and refreshes idempotently. | Wrong context/cluster/namespace UID, Secret UID, CA/endpoint, owner, environment, target object, credential ref, expired grant, replay, cross-environment read/write, stale/missing encryption posture evidence, excessive provider permissions. |
| Revocation/rotation | New revision acknowledged, consumer reload verified, old issuer credential rejected while retained data remains. | Partial delivery, consumer failure, old credential still usable, unreachable provider, issuer without revocation API; status remains unverified and no data resource is deleted. |

## Compatibility, maintenance, and next slice

No existing command, vault schema, or public MCP tool changes under RUG-446. Implement the RUG-8 authenticated-principal dependency first, then a local catalog validator and grant/state machine with synthetic canaries, then RUG-447's restricted SSH helper with a controlled SSH server fixture. Fake processes exercise delivery/output but cannot prove host-key verification. The first RUG-448 adapter should target one precreated named Kubernetes Secret only after the exact consumer, encryption posture evidence, and issuer revocation contract are documented. Public command/schema changes need a compatibility and migration review; old clients continue to use existing local commands, while cross-node operations reject clients that do not support this contract version.

Proposed contract owner: Miguel Lopez as WispKey maintainer for policy, grant storage, and audit; each destination owner maintains its host helper or environment consumer contract. This is a proposed assignment, not accepted ownership. The human owner for configuration, DEV-1/DEV-2 targets, and eventual rollout must be named during approval. Operator procedures must cover private catalog permissions, identity enrollment, key changes, cancellation, safe status, provider outage, rotation order, consumer reload, and disabling an operation. This document implements no runtime delivery. It records no approval, deployment, real-credential test, host-policy change, or rotation.
